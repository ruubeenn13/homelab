# 11 · Automatización — n8n

n8n v2.33.4 (Community) en `n8n.rubenlav.dev`. `N8N_ENCRYPTION_KEY` en `.env`
(copia en Bitwarden) — sin ella, las credenciales guardadas en los flujos son
irrecuperables. `GENERIC_TIMEZONE=Europe/Madrid` para crons en hora local.
Todo el estado (flujos, credenciales, SQLite) vive en `data/`: fuera de Git,
dentro del backup diario de Backrest.

## Canales ntfy

Dos topics (secretos, fuera de Git): el **personal** para infraestructura
(backups, batería, disco, errores) y el **familiar** para precios,
compartido con la familia vía el túnel (doc 12). Envío interno por
`http://ntfy:80` con cuerpo **JSON** (`topic`, `title`, `message`,
`priority`) — permite emojis y acentos también en el título.

## Workflows activos

- **Parte diario** (9:00) — estadísticas de AdGuard (Basic Auth, credencial
  cifrada en n8n) + monitores vía status page `homelab` de Uptime Kuma →
  topic personal; prioridad alta y alerta si hay caídas.
- **Precios del día** (8:00) — PVPC de REE (media + 3 horas más baratas y
  más caras; API pública, el precio del día se publica la tarde anterior)
  + gasolineras **Repsol de Elche y Crevillente** (95 y diésel, top 3 con
  localidad, dirección completa y horario; API del Ministerio,
  `FiltroProvincia/03`) → topic familiar.
- **Recordatorios** — mensual: restore de prueba de backups (norma
  CLAUDE.md); trimestral: disco, versiones pendientes, filtros AdGuard,
  Caps de B2 → topic personal.
- **Avisos de error (global)** — Error Trigger → topic personal con
  prioridad alta; asignado como *Error workflow* en los otros tres.

## Patrones y límites

- Servicios propios por URL interna (doc 08): `adguard:80`,
  `uptime-kuma:3001`, `ntfy:80`. APIs externas (REE, Ministerio) salen a
  internet sin problema — la limitación era solo de tráfico entrante.
- Webhooks entrantes **ya posibles** gracias al túnel (doc 12): bot de
  Telegram y push de GitHub, pendientes de implementar.

## Lección: Execute vs Publish (n8n 2.x)

**Execute ejecuta el borrador; el cron ejecuta lo publicado.** Editar un
workflow publicado crea un borrador y el cron sigue corriendo la versión
anterior hasta pulsar Publish (puntito naranja en el botón = cambios
pendientes). Batalla real: "Precios del día" corrió una madrugada con el
topic viejo por esto. Tras cualquier edición: Publish, siempre.

Actualización: el Parte diario (v2) añade métricas vía la API de consulta
de Prometheus (`/api/v1/query`): CPU, RAM, ocupación de NVMe y HDD y
uptime del host en el mismo push.
